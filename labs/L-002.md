# Lab L-002 – Fehlerhafte Release Notes untersuchen und korrigieren

**Modul:** M-002 · **Dauer:** 30 Minuten · **Format:** Zweierteam · **Tools:** Cursor, Git, pytest · **Projekt:** RelNotes

## Ziel
Sie beheben zwei abgegrenzte Parserfehler und dokumentieren deren Ursache und Auswirkungen.

## Lernziele
- Sie reproduzieren einen Fehler und formulieren eine überprüfbare Hypothese.
- Sie steuern zwei getrennte Agentenaufträge mit Tests und Diff-Review.
- Sie unterscheiden einen erfolgreichen Testlauf von einer vollständigen fachlichen Abnahme.

## Ausgangssituation
In den Release Notes fehlt die Kennzeichnung einer inkompatiblen API-Änderung. Außerdem wird ein Korrektur-Commit mit führenden Leerzeichen und großgeschriebenem Typ nicht verarbeitet.

> Ticket: `feat(api)!: ...` muss als Breaking Change erscheinen. `  Fix: ...` muss nach Normalisierung als Bugfix verarbeitet werden. Andere bisher akzeptierte Eingaben sollen unverändert funktionieren.

Die Korrektur von BUG-1 aus Demo D-002 muss im Team-Repository übernommen und geprüft sein. `python -m pytest tests/test_parser.py -q` meldet dann genau die Fehler `test_bang_markiert_breaking_change` und `test_grossschreibung_und_whitespace_werden_normalisiert`. Falls zusätzlich der Scope-Test scheitert, klären Sie den Übergabestand mit dem Trainer.

## Kernaufgabe – Level 1
### Schritt 1 – Fehler reproduzieren (5 Minuten)
Legen Sie einen Branch `fix/parser` an. Lesen Sie `parse_line()` und die beiden fehlgeschlagenen Tests. Notieren Sie für jeden Fehler Eingabe, erwartetes Verhalten und eine Ursache, die Sie im Code vermuten. Betrachten Sie auch die Ausgabe von `relnotes -i sample-data/commits.txt`.

### Schritt 2 – BUG-2 gezielt korrigieren (7 Minuten)
Beauftragen Sie zunächst nur die Verarbeitung des Ausrufezeichens. Lassen Sie im Plan-Modus Ursache, Dateien und Testschritte nennen. Prüfen Sie den Plan und starten Sie die Umsetzung. Vergleichen Sie Patch und Hypothese. Danach darf nur noch der Normalisierungstest fehlschlagen. Sichern Sie die Korrektur in einem Commit. Wechseln Sie anschließend die Rollen im Zweierteam.

### Schritt 3 – BUG-3 korrigieren und Gesamtstand prüfen (8 Minuten)
Die zweite Person führt den Agentenauftrag zur Normalisierung. Prüfen Sie, ob Großschreibung und führende Leerzeichen berücksichtigt werden und ob Typen danach konsistent verarbeitet werden. Führen Sie die gesamte Suite aus und prüfen Sie die Release Notes. Sichern Sie einen zweiten Commit.

```bash
python -m pytest tests/test_parser.py -q
python -m pytest -q
relnotes -i sample-data/commits.txt
```

## Optionale Vertiefung – Level 2
### Schritt 4 – Eine zusätzliche Prüffrage bearbeiten (bis 5 Minuten)
Ergänzen Sie einen sinnvollen Grenzfalltest oder schlagen Sie eine kurze Regel für künftige Fehleranalysen vor. Begründen Sie, welchen konkreten Fehler die Ergänzung erkennen bzw. vermeiden soll. Beide Parserkorrekturen gehören bereits zur Pflichtaufgabe.

## Hilfestellung nach dem eigenen Versuch
> Der Test test_bang_markiert_breaking_change schlägt fehl. Analysiere parser.py und den Test. Meine Hypothese lautet: [eigene Vermutung]. Plane eine minimale Korrektur nur für BUG-2 und benenne den Nachweis. Bestehende Assertions bleiben erhalten; BUG-3 gehört zum nächsten Auftrag. Beachte AGENTS.md und warte auf Planfreigabe.

Ersetzen Sie beim zweiten Auftrag Testname und Fehlerbeschreibung durch den Normalisierungsfehler.

## Beispiel für eine gute Lösung
Der Eintrag mit `!` erscheint unter „Breaking Changes“. Danas Korrektur wird unter „Bugfixes“ aufgeführt. Die Erklärung benennt die bisherige und die korrigierte Verarbeitung. Ob Regex oder String-Normalisierung verwendet wird, ist anhand von Lesbarkeit und Tests zu beurteilen.

## Done-Kriterien
- Beide Pflichtfehler sind korrigiert; BUG-1 bleibt korrigiert.
- Die Gesamtsuite hat keine fehlgeschlagenen Tests; zehn noch nicht implementierte Feature-Tests bleiben übersprungen.
- Bereits erfolgreiche CLI-Tests aus L-001 bestehen weiterhin. Die Anzahl zusätzlicher Tests kann je Team variieren.
- Zwei abgegrenzte Commits sowie Ursache und Nachweis sind dokumentiert. Level 2: Nutzen des Zusatztests oder der Regel ist begründet.

## Rolle-Checkliste
- Analyst: Fehler vor der Änderung reproduziert.
- Entwickler: je Fehler einen begrenzten Auftrag ausgeführt.
- Reviewer: Testnamen, Diff und fachliche Ausgabe verglichen.

## Reflexion (5 Minuten)
Welche eigene Hypothese hat sich bestätigt oder geändert? Welche Information aus den ausgeführten Werkzeugaufrufen half bei der Prüfung? Welche Fälle sind trotz erfolgreicher Suite noch nicht abgedeckt? Halten Sie die Antworten kurz fest.

## Typische Fehler
- Beide Fehler werden im ersten Auftrag vermischt: Änderungen getrennt prüfen.
- Ein Test wird übersprungen oder abgeschwächt: Teständerung zurücknehmen.
- Großschreibung wird akzeptiert, der Typ aber nicht normalisiert: Verarbeitung bis zur Gruppierung prüfen.
- BUG-3 bleibt als vermeintliche Zusatzaufgabe offen: beide Fehler vor M-003 abschließen.

## Zusammenfassung
Sie haben einen funktionsfähigen Ausgangsstand für neue Features. Vor Modul 3 werden die geprüften Änderungen in den vereinbarten Integrationsbranch übernommen. Der Trainer unterstützt bei einem noch unvollständigen Stand mit einer gemeinsam geprüften Referenzkorrektur.

# Lab L-001 – CLI-Ausgaben für automatisierte Aufrufe steuern

**Modul:** M-001 · **Dauer:** 30 Minuten · **Format:** Zweierteam · **Tools:** Cursor, Git, pytest · **Projekt:** RelNotes

## Ziel
Sie ergänzen eine begrenzte CLI-Funktion und prüfen deren Auswirkungen auf bestehende Aufrufe.

## Lernziele
- Sie formulieren aus einem fachlichen Auftrag überprüfbare Anforderungen.
- Sie prüfen einen Agentenplan und unterscheiden Nutzdaten von Statusmeldungen.
- Sie belegen die Änderung mit Tests und einem nachvollziehbaren Diff.

## Ausgangssituation
Das Release-Team ruft RelNotes in einem Skript auf. Die erzeugten Release Notes werden weiterverarbeitet; die zusätzliche Statistik ist in diesem Ablauf nicht erforderlich.

> Ticket: Ergänzen Sie `--quiet` und `-q`, um ausschließlich die Statistik auf stderr zu unterdrücken. Die Release Notes und das bisherige Verhalten ohne diese Option müssen erhalten bleiben.

Starten Sie im vorbereiteten Team-Repository. Lesen Sie `README.md` und `AGENTS.md`; prüfen Sie `git status` sowie die Tests. Am unveränderten Kursstart sind genau drei bekannte Parser-Tests fehlgeschlagen und zehn Feature-Tests übersprungen. `--version` aus der Trainerdemo ist keine Voraussetzung. Bei Einrichtungsproblemen arbeiten Sie mit Ihrem Partner am vorbereiteten Arbeitsplatz weiter.

## Kernaufgabe – Level 1
### Schritt 1 – Anforderungen formulieren (5 Minuten)
Leiten Sie vor dem Agentenaufruf vier Akzeptanzkriterien aus dem Ticket ab: beide Optionsnamen, unveränderte Nutzdaten, unveränderte Dateiausgabe und unverändertes Standardverhalten. Ergänzen Sie einen selbst gewählten Prüffall, beispielsweise den Erhalt einer echten Fehlermeldung trotz `--quiet`. Legen Sie mit `git switch -c feat/quiet` einen Branch an. Lesen Sie `src/relnotes/cli.py` und die vorhandenen CLI-Tests.

### Schritt 2 – Plan prüfen und umsetzen (10 Minuten)
Formulieren Sie einen eigenen Auftrag mit Ziel, betroffenen Dateien, Grenzen und Testauftrag. Wählen Sie im Cursor-Agentenfenster den Modus **Plan**. Prüfen Sie den Plan, bevor Sie die Umsetzung starten. Die drei bekannten Parserfehler gehören nicht zu diesem Auftrag. Ergänzen Sie Tests; schwächen Sie bestehende Assertions nicht ab.

### Schritt 3 – Ergebnis prüfen und sichern (5 Minuten)
Prüfen Sie den Diff und führen Sie gezielte Tests sowie die gesamte Suite aus. Vergleichen Sie Aufrufe mit und ohne Option: stdout bzw. die Ausgabedatei muss denselben Inhalt enthalten. Sichern Sie die Änderung und die Tests in einem Commit, z. B. `feat(cli): Statistik optional unterdrücken`.

```bash
python -m pytest tests/test_cli.py -q
python -m pytest -q
relnotes -i sample-data/commits.txt -q
```

## Optionale Vertiefung – Level 2
### Schritt 4 – Unklaren Auftrag präzisieren (bis 5 Minuten)
Beurteilen Sie den Auftrag „Reduzieren Sie die CLI-Ausgaben“. Nennen Sie zwei mögliche Fehlinterpretationen und formulieren Sie Rückfragen. Vergleichen Sie den überarbeiteten Auftrag mit Ihrem ersten Entwurf. Die fertige Implementierung bleibt erhalten.

## Hilfestellung nach dem eigenen Versuch
> Analysiere die CLI und ihre Tests. Plane die Optionen --quiet und -q: nur die Statistik auf stderr entfällt, Nutzdaten und Standardverhalten bleiben erhalten. Begrenze die Änderung auf CLI und passende Tests. Beachte AGENTS.md. Nenne zuerst Plan und Prüffälle; warte mit der Implementierung auf meine Freigabe.

## Beispiel für eine gute Lösung
Ohne Option erscheinen Release Notes auf stdout und die Statistik auf stderr. Mit `--quiet` oder `-q` erscheinen dieselben Release Notes, aber keine Statistik. Mit `--output` wird derselbe Dateiinhalt geschrieben. Ein Test nur auf leeres stderr genügt nicht: Er würde auch ein versehentlich vollständig stillgelegtes Programm akzeptieren.

## Done-Kriterien
- Beide Optionsnamen und ein selbst gewählter Prüffall sind getestet; Nutzdaten und Standardverhalten bleiben erhalten.
- Die CLI-Tests bestehen. In der Gesamtsuite scheitern nur die drei bekannten Parser-Tests; keine zuvor erfolgreichen Tests schlagen fehl.
- Der Diff enthält nur auftragsbezogene Änderungen und zusätzliche Tests.
- Commit und kurze Begründung der Abnahme liegen vor. Level 2: zwei Mehrdeutigkeiten und passende Rückfragen sind notiert.

## Rolle-Checkliste
- Auftraggeber: gewünschtes Verhalten und Grenzen festgelegt.
- Entwickler: Plan, Patch und Testausgabe geprüft.
- Reviewer: Nutzdaten und Standardverhalten ausdrücklich kontrolliert.

## Reflexion (5 Minuten)
Welche Anforderung war im ersten Auftrag noch unklar? Welcher Test würde eine falsche Unterdrückung von stdout erkennen? Wäre eine manuelle Änderung bei dieser Aufgabe schneller gewesen? Begründen Sie Ihre Einschätzung anhand Ihres Ablaufs.

## Typische Fehler
- stdout wird zusammen mit der Statistik unterdrückt: Nutzdatenvergleich ergänzen.
- Nur `--quiet` wird getestet: Kurzform `-q` zusätzlich prüfen.
- Bekannte Parserfehler werden ungefragt korrigiert: Auftrag begrenzen.
- Nur die Testanzahl wird verglichen: fehlgeschlagene Testnamen kontrollieren.

## Zusammenfassung
Sie verfügen über eine geprüfte CLI-Erweiterung und einen gesicherten Commit. In Modul 2 bearbeiten Sie die bekannten Parserfehler einzeln. Die erfolgreiche Quiet-Änderung bleibt Bestandteil Ihres Projekts.

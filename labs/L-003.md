# Lab L-003 – Versionsvorschlag implementieren und im Pull Request prüfen

**Modul:** M-003 · **Dauer:** 40 Minuten · **Format:** Zweierteam mit Peer-Review · **Tools:** Cursor, GitHub, pytest · **Projekt:** RelNotes

## Ziel
Sie übergeben eine fachlich begründete Feature-Änderung mit überprüfbaren Testnachweisen an einen Reviewer.

## Lernziele
- Sie leiten aus einem Issue Prioritätsregeln und Randfälle ab.
- Sie erstellen einen Pull Request mit Anforderungsbezug und konkreten Testnachweisen.
- Sie begründen die Annahme oder Ablehnung einer fremden Änderung.

## Ausgangssituation
Das Release-Team möchte eine Versionsnummer vorschlagen lassen. Mehrere Commit-Typen können gleichzeitig vorkommen; die Reihenfolge der Commits soll das Ergebnis nicht beeinflussen.

> Ticket: Implementieren Sie ISSUE-02 aus `docs/issues/ISSUE-02-semver.md`. Breaking Changes haben Vorrang vor Features, diese vor Fehlerkorrekturen. Ohne relevante Änderung bleibt die Version erhalten.

Startbedingung: Parserkorrekturen und Quiet-Funktion sind geprüft und im Integrationsbranch enthalten. Die Gesamtsuite ist ohne Fehler. Die Demo-Funktion `--types` ist für dieses Lab nicht erforderlich. Öffnen Sie ISSUE-02 über seinen Titel; tatsächliche GitHub-Issue-Nummern können abweichen.

## Kernaufgabe – Level 1
### Schritt 1 – Anforderungen und Randfälle klären (5 Minuten)
Notieren Sie vor dem Agentenaufruf den erwarteten Vorschlag von `2.3.1` für: Breaking Change plus Feature; Feature plus Fix; leere Commit-Liste. Lesen Sie das Issue und die zugehörigen Tests. Legen Sie vom aktuellen Integrationsstand den Branch `feat/issue-02-semver` an.

### Schritt 2 – Implementieren und PR vorbereiten (15 Minuten)
Formulieren Sie den Auftrag selbst. Prüfen Sie im Plan-Modus die betroffenen Dateien, Prioritätsregeln und Tests. Entfernen Sie ausschließlich den Skip-Marker von `test_issue02_semver.py`, wenn die Implementierung geprüft wird. Ergänzen Sie selbst gewählte Randfalltests. Führen Sie gezielte Tests und die Gesamtsuite aus. Öffnen Sie einen PR mit der Vorlage unter `.github/pull_request_template.md`.

```bash
python -m pytest tests/features/test_issue02_semver.py -q
python -m pytest -q
relnotes -i sample-data/commits.txt --suggest-version 2.3.1
```

### Schritt 3 – Peer-Review durchführen (10 Minuten)
Prüfen Sie den PR eines anderen Teams. Gleichen Sie Anforderungen, Diff und Testnachweise ab. Wählen Sie einen Randfall und überprüfen Sie dessen erwartetes Ergebnis. Formulieren Sie mindestens einen konkreten Befund mit Datei bzw. Anforderung und einer begründeten Entscheidung. Die anschließende Modulauswertung bietet Zeit für Rückfragen und Korrekturen.

## Optionale Vertiefung – Level 2
### Schritt 4 – Eine Erweiterung vorbereiten (bis 5 Minuten, nur bei ausreichender Restzeit)
Lesen Sie ISSUE-03 zur JSON-Ausgabe. Formulieren Sie Akzeptanzkriterien und den Änderungsplan. Eine Implementierung beginnt erst auf einem separaten Branch vom aktuellen Integrationsstand. Der Review der Pflichtaufgabe hat Vorrang; ein zweites Feature ist kein Pflichtziel.

## Hilfestellung nach dem eigenen Versuch
> Plane ISSUE-02 anhand des vollständigen Issue-Texts. Prüfe die Priorität Breaking > feat > fix/perf > unverändert sowie leere Eingabe und Reihenfolge. Beachte AGENTS.md. Nenne Dateien, Tests und offene Fragen; warte auf Freigabe. Bestehende Assertions bleiben erhalten; nur der Skip-Marker dieses Features darf entfernt werden.

## Beispiel für eine gute Lösung
Von `2.3.1` ergeben sich bei Breaking plus Feature `3.0.0`, bei Feature plus Fix `2.4.0` und bei leerer Liste `2.3.1`. Ein Review-Befund könnte lauten: „Der Test zur leeren Liste fehlt. Bitte ergänzen Sie den Nachweis für die Anforderung 'ohne relevante Änderung unverändert'.“ Die vereinfachte Kursregel für `0.x` ist im Issue ausdrücklich beschrieben.

## Done-Kriterien
- Alle Tests von ISSUE-02 werden ausgeführt und bestehen; die Gesamtsuite enthält keine Regressionen.
- Mindestens ein zusätzlicher begründeter Randfall ist getestet.
- Der PR nennt Problem, Änderung, ausgeführte Testbefehle und verbleibende Grenzen.
- Ein fremder Reviewer hat eine begründete Entscheidung dokumentiert. Bei einem einzelnen Teilnehmer übernimmt der Trainer die Reviewer-Rolle.
- Merge erst nach behobenen Befunden und vereinbartem Review. CI wird in M-004 ergänzt. Level 2: Anforderungen und Plan für JSON liegen vor.

## Rolle-Checkliste
- Autor: Anforderungen und Testnachweise vollständig beschrieben.
- Agent: auf freigegebenen Dateien und im vereinbarten Umfang gearbeitet.
- Reviewer: fachliche Prüfung durchgeführt, nicht nur Teststatus abgelesen.

## Reflexion (5 Minuten)
Welche Information fehlte zunächst im PR? Welcher Randfall war besonders aufschlussreich? Welche Änderung haben Sie aufgrund des Reviews vorgenommen? Tragen Sie Entscheidung und Begründung in `docs/arbeitsnachweis.md` ein.

## Typische Fehler
- Feature-Tests bleiben übersprungen: Testausgabe auf Skip-Status prüfen.
- Der Versionsvorschlag hängt von der Commit-Reihenfolge ab: Priorität testen.
- Der PR nennt „getestet“ ohne Befehle und Ergebnisse: Nachweise ergänzen.
- Eigener PR wird als Peer-Review bewertet: unabhängigen Reviewer einbeziehen.

## Zusammenfassung
Sie verfügen über einen geprüften Feature-PR. Vor M-004 wird der akzeptierte Stand integriert und die Suite erneut ausgeführt. Offene Befunde verhindern eine Release-Freigabe; sie werden nicht durch einen erfolgreichen einzelnen Test ersetzt.
